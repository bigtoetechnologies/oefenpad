A Dutch practice site for adult newcomers to the Netherlands, most of them studying for inburgering. The practice pages are static HTML with no build step and no framework. Sign-up and account management are a small .NET 10 service in server/. A companion paperback, Quick Wins in Dutch, lives in book.md; it was put on hold on 16 November 2026 and is not part of the offer (Docs/product.html §7).

The practice site is deliberately plain to deploy: open index.html over any static server and it runs. The account pages need the server in server/.

The documentation is HTML, and the HTML is the document. Every page under Docs/ is a .html file reached from Docs/index.html. The Markdown originals were converted in November 2026 and deleted, so there is no separate source to keep in sync and no doc build step: edit the page itself. Adding a document means writing a page in the same shell — sidebar, header, "On this page", previous/next — and putting it in the menu on every page and on the index. Never add a .md file under Docs/.

Non-negotiables

These come from Docs/decisions.html and are not yours to relax.

Rule Why
The interface is Dutch Most users have no English. Dutch chrome is itself practice
Meaning travels in pictures and colour Never in a sentence a learner must parse
No text inside artwork, ever One art set has to serve every first language
English glosses only, no other languages Learners use their own dictionary
Orange means "do this now", nothing else It may mark several elements if they are the same idea
Blue says what a thing is Cobalt #2B50C8, never the retired #1B3A6B
No souvenir Dutch imagery No windmills, clogs, tulips, canals, cheese

A feature that only works if the learner reads English is suspect. Say so rather than building it.

The design system

One stylesheet and one script for the whole site: assets/site/oefenpad.css and assets/site/oefenpad.js. Class names are Dutch. A twelve-column grid, hairline rules, heavy Archivo type, and colour applied as brush-painted fills. Full rules in Docs/designguide.html.

Two traps that have already cost a day

The painted fills look like plain rectangles if either of these is broken, and breaking one of them produces no visible change on its own, so you will think your fix did nothing.

  1. The painted SVG must use a fixed small viewBox — 300 × 150, or 100 × 30 with data-verf-klein — stretched by preserveAspectRatio="none". The filter's baseFrequency is tuned to those units. Use the element's real pixel size and the bristle texture falls below one pixel.
  2. verf() clears background-color after inserting the SVG. The paint layer is semi-transparent by design; the flat CSS background is only the no-JS fallback. Leave it opaque and it fills in every bristle gap.

Compare any change against Docs/design-options/g-penseelraster.html. That prototype is the agreed design and the reference for what the paint should look like.

Other things worth knowing

  • Bilingual markup. Every page ships both languages; <span lang="nl"> and <span lang="en">, switched by CSS on html[data-taal]. An inline script in <head> sets it before first paint.
  • Theme. Opens light always. The system prefers-color-scheme is deliberately ignored. oefenpad.js injects the #theme-toggle button; do not hand-write it into pages.
  • The games are React now. The six games live in client/ and are served from /spelen/<game> by the .NET host. GameShell renders the chrome: .vel, .balk, .spel-kop and .voet, with the title outside .app-container so its rule spans the sheet rather than the 720 px game column. The games are Dutch-only, so their .balk has no .taal switch; .rechts holds only the injected #theme-toggle. The browser gets one round at a time from the game API; the word bank and the puzzle generators are server-side.
  • The lexicon is a 10,000-lemma Dutch word list. tools/lexicon/ holds the list through B2, classified by part of speech, theme and semantic domain, with our own five-band frequency scale (Start, Basis, Midden, Gevorderd, Verdieping) because no public B2 list exists and the coursebook's A1/B1/open tier is not a level. Nothing on the site reads these files yet. A list of words in a language is not copyrightable; the only licence obligation is the CC BY-SA copyleft from the kaikki rows. Docs/lexicon/index.html has the pipeline and the scale; Docs/lexicon/bronnen.html has every source and the exact selection rule. The generated TSVs are tracked in git; commit them with the scripts that produced them.

Running and checking it

Port 8080 is often in use by something of the owner's. Leave it alone.

python3 -m http.server 8099 --bind 127.0.0.1

To check a visual change, screenshot it headless and compare against the prototype:

google-chrome --headless=new --disable-gpu --no-sandbox --hide-scrollbars \
  --window-size=1400,1000 --virtual-time-budget=7000 \
  --user-data-dir=/tmp/fresh-profile \
  --screenshot=out.png "http://127.0.0.1:8099/index.html?v=1"

Chrome caches aggressively here and will hand you a stale render. A screenshot that contradicts the DOM is the symptom. Use a fresh --user-data-dir and a changing query string for every shot that matters. Two separate wrong conclusions in this repo came from skipping that.

Measuring beats eyeballing: sample pixels with PIL rather than judging a downscaled screenshot. Brush texture shows up as a spread of roughly 17–20 in the blue channel down a tile; a flat fill measures 0.

The account system is a separate .NET 10 solution under server/. Port 8098 is for it; leave 8080 alone.

ASPNETCORE_ENVIRONMENT=Development dotnet run \
  --project server/Oefenpad.WebUI --urls http://127.0.0.1:8098

dotnet test server/Oefenpad.Tests

It applies migrations on start. The SQLite database is server/Oefenpad.WebUI/oefenpad.db; account email is written to server/Oefenpad.WebUI/email-sink/ when no SMTP host is configured. Do not serve the repo root to the web app: only assets/ and the WebUI wwwroot are exposed, and that is deliberate — the old src/ scripts and word banks are gone.

The React games build into the host. dotnet build and dotnet publish run npm ci (when node_modules is missing) and npm run build, so a normal build ships the games; -p:SkipClientBuild=true builds the server alone. The npm step is skipped when the client sources are unchanged.

cd client && npm run build                    # writes wwwroot/spelen by hand
cd client && npm run scope-css                # after a change in styles/source

Docs/games-backend.html has the API, the round model, the verification record and what stays in the browser.

Where things stand

All nine pages — home, the two legal pages, six games — are on one design system, the six games under the same .balk and .voet chrome. The home and legal pages are bilingual and still static; the games are Dutch-only, React, and served by the .NET host from /spelen/, with their content behind /api/games.

Voorzetselpaden (now client/src/games/prepositions/, scenes in assets/voorzetselpaden/) is the newest: a pilot with twenty-eight levels — ten A0 chunks and eighteen A1 chunks, each taught across two to four example scenes, ninety-one in all — and the only game whose art is raster. Its ninety-one scene images are alpha masks drawn on a cobalt block, so they need no second file for dark mode. Docs/game-art.html has the art technique; Docs/prepositions-implementation.html describes how the game is built, and Docs/prepositions.html is the spec behind it.

The scene plans are HTML now, and they are the master. The seven Markdown plans were replaced on 12 November 2026 by eight pages under Docs/voorzetselpaden/ — A0, A1, A2, A2 pairs, A2+, B1, B1+, B2 — holding 713 chunks and 1015 cards, 271 of them proposals with no art yet. Cards group by contrast set, so wachten op sits beside wachten voor, and each chunk's own examples sit together with a count that turns red below three. A card holds the chunk, the gloss, the scene brief, Must read, Avoid, the review verdict and — for the ninety-one examples that are in the game — the example sentence, the build sentence and the control question. A batch is one chunk; its Grok prompt is built from the cards when it is needed (tools/grok/grok.py prompt), so it never goes stale. The old Markdown prose is in git history, no longer on the pages. Edit the HTML, not prepositions.json: the game data is generated from these pages. The originals are in git at 80e688c.

It is also the only game with a gate: the A0 band is free, the whole A1 band needs an account, and A2 and up will need a paid plan, which is not built yet (so that slice is empty). The first level of a band opens the band; within it a level opens only when the learner has finished the one before it (server/Oefenpad.Services/Games/GameAccessService.cs).

The product decision changed on 16 November 2026: Docs/product.html §7 sets two free themes (Boodschappen, Mensen) at A1 and below, six weeks of full access on sign-up, then €10/month or €100/year, with a frozen read-only log after cancelling. That gate is not built, and cannot be until themes exist — Voorzetselpaden's 713 chunks carry no theme tag (product.html §12). The code still enforces the band slice above.

Sign-up and account management live in the .NET 10 solution under server/. It is Razor Pages, not Blazor, with ASP.NET Core Identity and SQLite, and it serves the static site alongside the account pages from the same host. The pages are bilingual and use the same oefenpad.css. Docs/accounts.html has the architecture, the flows, the rate limits and what must change before accounts go live. Docs/accounts-handover.html is the session record: the decisions behind the build, the verified build/test evidence, and a file-by-file map so the next agent does not have to load the solution.

The remote is git@github.com:bigtoetechnologies/oefenpad.git; main is 8 commits ahead and unpushed, so the whole redesign exists only on this disk. Uncommitted on top of that: the game chrome, the whole React client, the server-side game content and API, the removal of the old src/ game pages, and the docs that describe it. Push only when the owner asks.

Working style the owner expects

  • Lead with the answer. Keep it short; expand only when asked.
  • Disagree when you think he is wrong, in the first line, with the reason.
  • Delegate to sub-agents wherever the task allows it. This repo's reading is heavy and the main context fills up fast, so use spawn_agent for work that is self-contained: reading a set of docs to answer one question, drafting a document, running a build or test suite and reporting only the failures, auditing a batch of cards. Each agent starts blank — give it every path, rule and constraint it needs, keep write scopes disjoint when several run in parallel, and ask for a short report rather than a transcript. Do the small surgical edit yourself; coordination costs more than it saves.
  • Never report something as working without having run it.
  • Show visual changes before committing to them. A one-line description of a colour change is not enough for him to judge it, and a change he approved from a description has already had to be reverted once.
